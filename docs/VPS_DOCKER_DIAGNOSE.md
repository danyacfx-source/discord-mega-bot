# DENDICH / RADIO SILENCE — диагностика Docker на VPS

Если `docker compose build bot` проходит, но бот завершается после деплоя,
не удаляйте PostgreSQL volume или `./data`. Ошибка может возникать во время
запуска процесса, а не на этапе сборки образа.

## Безопасная диагностика без изменения контейнеров

Зайдите по SSH на VPS, перейдите в папку проекта с `docker-compose.yml` и выполните:

```bash
bash scripts/vps_docker_diagnose.sh
```

Скрипт проверяет Docker Compose, показывает состояние **только сервисов текущего
Compose-проекта**, код завершения `bot`, флаг OOM, число перезапусков, состояние
PostgreSQL, доступное место и память. Он не останавливает и не перезапускает
контейнеры и не читает содержимое томов.

**Секреты:** скрипт не печатает значения переменных окружения или логи
приложения. Однако сообщения об ошибках самой команды `docker compose config`
теоретически могут включать данные из пользовательской конфигурации —
прочитайте вывод перед публикацией.

### Расшифровка результатов

- `Exited`, `ExitCode=1`: стартовый процесс завершился с ошибкой; следует
  отдельно изучить traceback в логах `bot`.
- `OOMKilled=true` или `ExitCode=137`: проверьте память хоста и заданный
  Docker memory limit; код 137 сам по себе не доказывает OOM.
- `Health=unhealthy`, `Status=running`: контейнер жив, но healthcheck не проходит.
- `No bot container found`: сбой до создания контейнера, например во время
  обработки Compose-конфигурации или деплоя в панели хостинга.
- `postgres` отсутствует: PostgreSQL может быть внешним сервисом; не следует
  считать это неисправностью само по себе.

Для анализа логов **только после проверки на возможные секреты**:

```bash
docker compose --profile postgres logs --no-color --tail=80 bot
```

Для обновления только бота без пересоздания PostgreSQL (при готовом образе):

```bash
docker compose --profile postgres up -d --no-deps --no-build bot
```

**Не используйте** `docker compose down -v` или очистку Docker volumes: эти
действия могут удалить сохранённые данные PostgreSQL.
